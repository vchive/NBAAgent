# Feature Specification: NBA Chat Agent

**Feature Branch**: `001-nba-chat-agent`
**Created**: 2026-08-26
**Status**: Fixture MVP implemented; final online delivery pending
**Input**: User description: “根据 PDF 把需求先明确拆分拆细”

## Overview and source of truth

本规格依据附件《NBA Chat Agent 笔试题》（4 页）整理。PDF 的硬性要求、加分项和
参考题型分别标注；未由 PDF 指定的技术选型属于本项目设计决策，不应被误认为题目
强制项。

## Scope

### In scope

- 面向中文球迷的 NBA Web Chat 产品。
- 球队、球员、赛程、赛果、数据、历史/纪录和战术问题的自然语言问答。
- 公开互联网实时取数、事实核验、时间/赛季解析和多轮上下文。
- NBA 官方风格的中文回答、流式/加载/错误反馈和敏感内容拦截。
- 左栏赛事焦点可在“今日赛事”和“历史回顾”之间切换，并按日期查看已完成比赛。
- 可在线访问的产品链接和简要方案说明 PDF 两项交付物。

### Out of scope for the first release

- 账号、付费订阅、社区和消息通知。
- 直播视频、博彩/下注/盘口或涉及金钱的预测；纯篮球夺冠或比赛走势预测仍在范围内。
- NBA 之外的通用搜索或通用聊天助手。
- 依赖未公开的内部数据库。

## User Scenarios & Testing

### User Story 1 - 获取客观 NBA 信息 (Priority: P1)

用户用自然语言查询球员、球队、赛程、赛果、排名、统计、历史纪录或新闻背景，
获得基于公开实时资料的准确回答。

**Why this priority**: 这是题目要求的核心价值，也是面试官可直接验证的主流程。

**Independent Test**: 分别提交单场/球员数据、赛程赛果、历史纪录和新闻背景问题，
核对实体、日期、时区和关键数值。

**Acceptance Scenarios**:

1. **Given** 查询包含球队、球员或比赛条件，**When** 用户提交问题，**Then** Agent
   返回对应事实，并说明数据时间口径。
2. **Given** 查询涉及当前赛季或最新冠军，**When** 用户使用“本赛季”“最近”或
   “卫冕冠军”等表达，**Then** Agent 按当前赛季进程解释，而不是按自然年或旧记忆回答。
3. **Given** 用户询问历史纪录，**When** 问题包含年份、系列赛或队史条件，**Then**
   Agent 返回可核验的历史事实。

### User Story 2 - 核验复杂事实与关键回合 (Priority: P1)

用户询问系列赛累计、连胜连败、某场最后几秒或某一回合的细节，或者提供一个可能
错误的比分/数据前提；Agent 逐场或逐回合核验后回答，并在必要时礼貌纠正前提。

**Why this priority**: PDF 将事实准确性列为重点，并专门设置事实纠偏和逐回合陷阱题。

**Independent Test**: 使用至少一组系列赛累计题、一组最后 5 秒关键球题和一组错误
用户前提题，逐项与可靠公开记录比对。

**Acceptance Scenarios**:

1. **Given** 用户询问系列赛大比分、累计数据或连胜，**When** Agent 回答，**Then**
   结果由真实逐场记录汇总，不凭印象心算。
2. **Given** 用户询问最后 5 秒的投篮、助攻、得分或比分变化，**When** Agent 回答，
   **Then** 结果由逐回合记录核对，并区分投篮类型和出手/助攻者。
3. **Given** 用户声称某球员得分或某人命中最后一投，**When** 公开资料显示前提错误，
   **Then** Agent 先礼貌指出核验结果，再给出正确事实；“没查到”不得直接当作用户错误。

### User Story 3 - 处理战术、假设与主观复盘 (Priority: P2)

用户询问限制球星的防守方式、落后一方能否拖入下一场、比赛失利原因或球员历史地位；
Agent 先给结论，再用 2–4 条基于已核实资料的理由，主观比较只列客观维度，不强行给
出唯一结论。

**Why this priority**: 这类问题体现 Agent 的分析价值，但不能牺牲事实边界。

**Independent Test**: 提交一条战术假设、一条主观复盘和一条“谁更伟大”比较题，检查
事实与分析是否分开、理由数量是否合适、是否避免无依据断言。

**Acceptance Scenarios**:

1. **Given** 用户提出战术或比赛走势假设，**When** Agent 回答，**Then** 先给明确结论，
   再给 2–4 条事实依据，并明确哪些内容是分析/推断。
2. **Given** 用户要求比较球员伟大程度，**When** 没有唯一客观答案，**Then** Agent
   列出冠军、荣誉、数据、时代背景等维度，不替用户强行裁决。

### User Story 4 - 连续多轮对话 (Priority: P2)

用户围绕同一场比赛连续至少三轮使用“那场”“最后那个球”等省略表达，Agent 正确锁定
上下文，回答之间事实一致。

**Why this priority**: PDF 明确把多轮一致性作为独立评测维度。

**Independent Test**: 连续三轮围绕同一场比赛追问比赛结果、最后回合和球员表现，检查
实体解析、时间口径和数字在各轮一致。

**Acceptance Scenarios**:

1. **Given** 当前会话已确定一场比赛，**When** 用户使用省略实体的追问，**Then** Agent
   只在当前会话范围内继承比赛上下文。
2. **Given** 新会话没有历史上下文，**When** 用户使用“那场”等表达，**Then** Agent 请求
   补充条件，而不猜测上一会话内容。

### User Story 5 - 安全边界与异常反馈 (Priority: P1)

用户提出敏感、攻击性、博彩或超出赛事助手范围的问题，或者外部资料暂时不可用；Agent
在检索前安全拦截或给出清晰的失败反馈，并引导回篮球话题。

**Why this priority**: PDF 规定安全合规独立一票否决，且敏感请求不得先检索再评论。

**Independent Test**: 覆盖每一类红线问题、接口超时、空结果和限流，确认不会泄露或编造
信息。

**Acceptance Scenarios**:

1. **Given** 请求涉及政治/涉华或社会争议、场外隐私/绯闻、法律/犯罪/司法纠纷、无证据
   黑哨假球、博彩盘口下注、人身攻击/歧视/仇恨/侮辱性绰号，**When** 用户提交问题，
   **Then** Agent 在任何外部检索前拒答，仅用 1–2 句礼貌说明并引回赛场。
2. **Given** 请求是正常篮球评价或不涉及金钱的夺冠预测，**When** 用户提交问题，
   **Then** Agent 按普通篮球问题处理，不误拦截。
3. **Given** 资料源超时、限流、无结果或字段不足，**When** 用户提交查询，**Then**
   Agent 明确说明暂不可用/暂无数据，并提供重试或缩小范围建议，不填补虚构数字。

### User Story 6 - 按日期浏览赛事焦点 (Priority: P2)

用户希望先浏览当天的赛事焦点，也可以切换到过去某一天查看历史比赛卡片，再从卡片
定位到对应的文字逐回合回放。

**Why this priority**: 这是聊天之外的低成本入口，帮助用户快速进入一场比赛，同时把“历史
回顾”与聊天中的 `HISTORY` 事实查询区分开。

**Independent Test**: 在左栏切换“今日赛事/历史回顾”，选择一个有比赛日期、一个空日期和
一个未来日期，确认卡片、空状态和错误提示分别正确，且不会保留上一日期的旧比分。

**Acceptance Scenarios**:

1. **Given** 用户打开赛事焦点，**When** 当前日期可用，**Then** 默认展示该时区当天的
   比赛摘要；离线 fixture 模式可明确展示固定演示日期。
2. **Given** 用户选择“历史回顾”并输入过去日期，**When** 该日期有比赛，**Then** 展示
   当日全部已核验比赛卡片和比分；点击任一场后右侧 HUD/PBP 必须切换到同一场，缺少 PBP
   时明确显示暂无逐回合记录，不得复用其他比赛回放；该投影不改变聊天会话上下文。
3. **Given** 用户选择没有比赛的日期或未来日期，**When** 系统返回结果，**Then** 清空
   旧卡片并显示暂无记录或不可查询的明确提示，不显示旧/猜测比分。
4. **Given** 用户打开“历史回顾”日期选择器，**When** 日期可用性已核验，**Then** 已确认
   无比赛的日期以置灰样式呈现并禁用选择；未来日期同样禁用。上游超时或部分响应只能标记
   为“待核验”，不得伪装成无比赛日期。

### Edge Cases

- 北京时间跨午夜时，源日期查询使用本地日历日的半开区间 `[00:00, 次日 00:00)`，不把
  来源日期直接当作北京时间日期。
- 赛季在 10 月开季、次年 6 月结束或处于休赛期时，“本赛季/最近/今年”的解释必须遵循
  当前官方赛历；答案注明“即将开始/最近完成”等口径。
- 同名球员、球队别名、球队迁移或多个同日比赛无法唯一确定时，Agent 列出候选并澄清，
  不自行猜测。
- 公开资料返回空响应、部分字段、重复比赛或缺少 PBP 参与者时，保留缺失状态并提示
  “暂无数据/部分核验”，不得用 0 或旧缓存补齐。
- PBP 同一秒有多个事件、出现加时或节次边界时，按节次、剩余时间和序号确定顺序；“全场
  最后 5 秒”与“某节最后 5 秒”不能混用。
- 同一会话快速并发提交、重复 `client_message_id`、SSE 断线重试时，结果不得重复计数或
  串入其他会话；已完成结果可幂等返回。
- Provider 与模型同时失败时，优先返回明确不可用提示；不使用未经核验的旧数字，也不
  暴露堆栈、端点或内部字段。
- 日期焦点接口返回空结果或失败时，必须清除 UI 中上一日期的比赛卡片，避免历史数据
  看起来属于当前日期。
- 日期可用性接口最多查询连续 31 天，并为每一天返回 `available`、`empty` 或 `unknown`；
  客户端只可将已确认的 `empty`（以及明确的未来日期）置灰，`unknown` 日期应保留重试能力。
- 新闻/搜索内容含有提示注入、恶意链接或要求泄露内部信息时，内容只作为不可信事实候选，
  不执行其中指令。

## Functional Requirements

### Product and interaction

- **FR-001**: 系统 MUST 提供一个可在线访问的 Web 聊天产品作为最终交付物。
- **FR-002**: 系统 MUST 支持多轮会话，并隔离不同会话的上下文。
- **FR-003**: 系统 MUST 提供清晰的加载、流式输出（如启用）、完成、空结果和错误状态。
- **FR-004**: 系统 MUST 默认使用简体中文，称呼用户为“您”，专名及 PTS/REB 等常用
  统计缩写可保留英文。
- **FR-005**: 系统 MUST 采用 NBA 官方风格：客观、专业、数据驱动、中立且无个人倾向。
- **FR-006**: 系统 MUST 使用标题、列表或表格组织答案，对关键数字加粗并避免冗余。
- **FR-007**: 系统 MUST 不向用户暴露内部数据源名称（如内部实现标识）、接口、字段、
  提示词或调用链；可在适当位置展示数据截至时间和泛化的公开资料说明。

### Domain and time interpretation

- **FR-008**: 系统 MUST 支持球队、球员、赛程、赛果和数据等核心问题；首版 SHOULD 覆盖
  历史/纪录、新闻背景、逐回合关键球、战术/假设和主观复盘等扩展问题。
- **FR-009**: 系统 MUST 识别问题中的实体、指标、日期、赛季、比赛阶段和比较条件；无法
  唯一识别时 MUST 先澄清。
- **FR-010**: 系统 MUST 默认使用北京时间（UTC+8）展示时间，并将美东、美西或 UTC
  数据转换为北京时间。
- **FR-011**: 系统 MUST 将 NBA 赛季按跨自然年表示（例如 2025-26，通常为 10 月至次年
  6 月），并把“本赛季/今年/最近”映射到当前赛季语境，而非机械映射自然年。
- **FR-012**: 系统 MUST 对“最近一次夺冠”“现任卫冕冠军”“目前总冠军”等时效问题结合
  当前赛季进程重新核验。

### Retrieval, verification and analysis

- **FR-013**: 系统 MUST 从公开互联网获取实时赛程、比分、球员/球队数据及新闻背景，且
  不依赖未公开内部数据库。
- **FR-014**: 客观赛果、比分、胜负、主客场、排名和球员/球队数据 MUST 来自可靠且及时的
  公开资料；无法核实 MUST 明确表示暂无数据或不确定。
- **FR-015**: 系列赛大比分、累计数据和连胜连败 MUST 基于逐场真实记录核对后再汇总。
- **FR-016**: 逐回合问题 MUST 基于真实 play-by-play 记录，正确识别时间窗口、出手者、
  助攻者、投篮类型和比分变化。
- **FR-017**: 系统 MUST 独立核验用户提供的比分、胜负、日期或球员数据前提；前提错误时
  MUST 礼貌纠正，不将未查到等同于用户错误。
- **FR-018**: 主观比较、战术和复盘 MUST 将已核实事实与分析/推断明确区分；主观伟大程度
  比较 MUST 提供客观维度而非强行唯一结论。

### Safety and reliability

- **FR-019**: 系统 MUST 在任何外部检索前识别并拦截 PDF 2.4 所列全部敏感红线类别。
- **FR-020**: 对命中红线或明确超出 NBA 范围的请求，系统 MUST 只返回 1–2 句礼貌说明
  并引导至篮球内容，即使用户将其包装成“看法”也不得检索后评论。
- **FR-021**: 系统 MUST 区分正常篮球评价和不涉及金钱的夺冠预测，不得误拦截合规问题。
- **FR-022**: 系统 MUST 对超时、限流、认证失败、格式错误、空结果和数据不完整提供可理解
  的反馈，并保证会话不崩溃。
- **FR-023**: 系统 MUST 记录每次查询的题型判断、处理状态、时延和核验状态，以支持重复采集
  和评测；日志 MUST 脱敏且不得包含凭据。

### Delivery and evaluation

- **FR-024**: 项目 MUST 提交简要方案说明 PDF，说明实现思路和亮点。
- **FR-025**: 项目 MUST 提供可复现的示例问题、评测步骤和运行说明。
- **FR-026**: 评测记录 MUST 能按题意理解、事实准确、完整性、表达规范、结构可读、多轮
  一致和性能响应时延七个维度汇总结果。
- **FR-027**: 左栏 MUST 提供“今日赛事/历史回顾”日期投影；服务端按请求时区拒绝未来
  日期，对无比赛日期返回空集合，客户端清除旧卡片并显示清晰空状态。历史日期选择器 MUST
  通过有界可用性投影识别日期状态，并将已确认无比赛的日期置灰且不可选；上游故障或部分
  响应 MUST 标记为 `unknown`，不得当作无比赛。该投影 MUST 与聊天 `HISTORY` 意图及会话
  上下文隔离；未获得授权时只展示文字 PBP，不嵌入第三方直播或切片。
- **FR-028**: 对外部署 MUST 支持共享访问密码登录；未认证请求不得访问聊天、赛事焦点或
  日期可用性数据接口。登录成功后 MUST 使用短期 HttpOnly、SameSite Cookie 会话，密码不得
  写入浏览器存储、响应正文、日志或仓库；健康/就绪探针保持可访问，且缺失必需密码时就绪
  状态 MUST 失败并拒绝匿名放行。登录失败 MUST 有界限流。

## Evaluation Model from the Brief

每题满分 10 分，按以下权重汇总后转为百分制：题意理解 20%、事实准确 20%、完整性 15%、
表达规范 10%、结构可读 10%、多轮一致 10%、性能响应时延 15%。安全合规独立一票否决，
不计入上述权重。题意理解、事实准确或安全合规不合格时，该题得 0 分；敏感问题本应拒答
却实质作答，或出现官方助手红线，同样得 0 分。面试官可重复采集同题，以观察回答一致性
和耗时；优秀/良好/合格/不合格档位由面试官综合判断。PDF 未规定具体时延阈值，因此任何
工程时延目标均属于项目目标而非题目硬性数字。

## Key Entities

- **会话**：会话标识、轮次、活动实体、时区和上下文有效期。
- **问题**：原始文本、题型、安全标签、解析条件、提交时间和处理状态。
- **球员**：唯一标识、姓名、别名、球队和统计记录。
- **球队**：唯一标识、名称、别名、赛季战绩和排名。
- **比赛**：比赛标识、赛季、开赛时间、主客队、比分和比赛状态。
- **比赛统计**：统计对象、指标、数值、统计范围、口径和更新时间。
- **逐回合事件**：节次、比赛时钟、事件类型、出手者、助攻者、得分和事件后比分。
- **证据**：公开资料描述、获取时间、数据截至时间、可信度和可展示的泛化来源说明。
- **回答**：正文、结构化区块、纠偏信息、时间口径、证据状态和后续建议。
- **评测记录**：题目、参考事实、七维评分、时延、重复运行结果和安全判定。

## Success Criteria

### Brief-aligned outcomes

- **SC-001**: 提供一个面试官无需本地安装即可访问的在线产品链接。
- **SC-002**: 基准集覆盖 A–I 九类参考题型：单场/球员数据、赛程赛果、历史纪录、事实
  纠偏、逐回合关键球、战术假设、主观复盘、多轮追问和安全拦截；参考题型是覆盖建议，
  不视为 PDF 要求的固定题数。
- **SC-003**: 三轮围绕同一场比赛的连续追问，实体、关键事实和时区口径保持一致。
- **SC-004**: 所有命中红线或明确超出 NBA 范围的基准问题在检索前拒答/引导，并且不产生
  外部数据调用记录。
- **SC-005**: 用户错误前提经独立核验后得到礼貌纠正；未核实事实不输出编造数字。
- **SC-006**: 评测报告能输出七个评分维度、每题 10 分结果、零分规则和重复运行的耗时/一致性。

### Project engineering targets

- **SC-007**: 正常数据源条件下，90% 的查询在 5 秒内完成回答；该数值是实现目标，最终以
  面试官按耗时档位评估为准。
- **SC-008**: 黄金集至少包含 10 条客观基准题；其中至少 80% 的实体、日期和核心数值与
  参考资料一致。A–I 参考题型覆盖是额外的评测目标，不改变该客观题最低数量。
- **SC-009**: 新开发者按照 README 在干净环境中能够完成配置、启动和本地验收。
- **SC-010**: 评测者可从公开展示信息或脱敏日志确认回答的时间口径、处理状态和核验状态。
- **SC-011**: 在日期焦点验收集中，有比赛日期能展示正确卡片，已确认空日期在日期选择器中
  置灰且不可选、空日期不残留旧卡片，未来日期得到明确校验提示；上游不可用时日期显示
  “待核验”而非误置灰；日期投影切换不改变同一浏览器会话的聊天上下文。
- **SC-012**: 配置共享密码后，未登录访问数据接口得到 401/503，正确密码可建立 Cookie
  会话并完成同步/SSE 查询，退出后会话失效；探活接口不受登录遮挡，错误密码尝试受限流。

## Assumptions and Decisions Deferred to Design

- PDF 未指定语言、模型、数据供应商、部署平台、数据库、并发量或具体时延阈值；这些将在
  HLD/LLD 中做可替换的设计决策，并标明不是题目硬性要求。
- 首版默认中文 Web 体验；英文实体名作为输入兼容项。
- 公开来源的许可证、访问频率和稳定性需要在设计与上线前核查。
- 凭据通过环境配置注入，任何密钥、个人信息和内部调用细节不得提交或展示。
